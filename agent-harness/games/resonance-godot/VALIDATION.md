# 실제 검증 체크포인트

환경: Godot 4.6.3, Linux, 120Hz 2D 물리. 검사 명령과 종료 코드는 `evidence/*.log`에 기록했다. 최초 harness check 종료0, Python unittest 5/5 종료0도 보존했다.

| 최종 검사 | 결과 | 증거 |
|---|---|---|
| 도형·정산·잔향·특수·스킬 규칙 | 121 checks, 실패0, 종료0 | `rules-final.log` |
| 물리·입력·저장 통합 | 2,603 checks, 실패0, 20 안정 보드, 종료0 | `battle-verified.log` |
| 같은 초기 스냅샷/스킬/과충전 정책의 두 선택 정책 | 두 정책 모두 전투 승리, 패배 fixture·재시작 통과, 종료0 | `full-battle-balanced-inlets.log` |
| 네이티브 렌더·입력 영상 | 실제 버튼/터치 이벤트로 첫 턴, 대형 폭탄 획득/사용·회복·리필. 종료0 | `native-movie.log`, `godot-battle.mp4` |

통합 검사의 최대 폴리곤 교차 면적은 8.794921875 world-unit², 최대 안정화 시간은 시뮬레이션 기준 약4.008초다. 엔진 접촉 허용 오차가 있어 교차 면적 0이라고 주장하지 않는다. 접촉 그래프는 공통 외곽선의 거리1.0 이내이며, 외형·충돌체·터치 영역이 같은 폴리곤인지 실제 검사했다. 실제 제거된 이전 ID 집합을 미리보기와 비교했다.

초기 실패도 삭제하지 않았다. 부모 보드 scale이 RigidBody2D의 실제 충돌과 스냅샷 좌표를 다르게 만들던 문제를 물리 노드 scale1로 고쳤다. 작은 리필이 매번 왼쪽에서 시작해 한쪽에 쌓이던 결함과 단순 순환 투입으로도 생긴 경계 넘침은 각 투입 열의 실제 쌓임 높이를 보고 낮은 곳에 새 기물을 투입하도록 고쳤다. 기존 기물 transform을 재배치하거나 접촉 허용 반경을 넓히지 않았다. 수정 후 동일 완주 검사가 통과했다. 실패 로그 이름에 `first`, `diagnosis`, `refill-fix`가 포함돼 있으며 최종 통과 로그와 구분한다.

영상은 Godot Movie Maker의 고정60fps 출력 1,310프레임(약21.83초)이다. 실제 기록에는 약56초가 걸렸으므로 **실시간60fps 성능 측정이 아니다**. headless 완주 결과를 영상으로 합성하지 않았다. 네이티브 첫 턴을 소프트웨어 OpenGL에서 직접 렌더한 화면이다. 기존 크기별 렌더 검사는 360×640, 390×844, 720×1280, 1280×900 창에서 종료0이었다. 고정9:16 콘텐츠 viewport 캡처이므로 긴/넓은 창의 여백은 PNG에 포함되지 않는다. **크기별 probe 로그를 다시 대조하니 720×1280 외 세 크기에서는 합성 터치가 정산을 만들지 않았다.** 이 세 크기는 렌더만 확인한 것이며 입력 성공으로 보고하지 않는다. 자동 입력의 창/viewport 좌표 변환과 실제 축소 창 터치 동작은 후속 확인이 필요하다. 720×1280 영상에서는 실제 이벤트로 스킬·기물 정산·리필까지 확인했다.

## 미완료 및 한계

- 새 주인공 대기/공격 PNG가 프록시403으로 도착하지 않아 동일 캐릭터 애니메이션·초상 통합은 미완료다. 현재 전경은 기존 독자 적 시트의 첫 적이며 새 주인공으로 제시하지 않는다.
- Kenney 파일도 미수신이다. 현재 효과는 Godot CPUParticles2D와 직접 그린 링/플래시이며 다운로드한 VFX나 커스텀 셰이더는 없다.
- Android SDK/JDK 개발 도구/export template·실기기 검증이 없어 APK를 만들지 않았다. 키보드·소프트웨어 터치 경로 검사는 실기기 접근성 인증이 아니다.
- Godot 물리의 기기·엔진 간 결정론은 보장하지 않는다. 동일 스냅샷의 전투 계산과 물리 안정성 검사는 별개다.
- 자동 완주나 렌더 성공만으로 재미·최종 아트 품질을 입증했다고 하지 않는다. 사람의 플레이 검수와 전송 문제 해결이 남아 있다.
- 한 전투만 구현했다. 웹판의 여섯 층 탐험 전체 이식·웹 저장 호환·배포·main 병합은 하지 않았다.
