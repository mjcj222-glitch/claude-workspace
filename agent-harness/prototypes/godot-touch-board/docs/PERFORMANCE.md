# 모션 계산 성능 개선 — 2026-10-21

임의 재배치를 다시 도입하지 않고 충돌 계산의 데이터 접근만 바꿨습니다. 같은 초기 시드·보드와 결정적 선택 순서에서 일반2~3개 소거 10건(2회 실행)은 **674–920ms**, 긴35개/특수2개 연쇄2건은 **2703–2716ms**였습니다. 누름→렌더 완료12건은 **31.5–49.2ms**였습니다. 이 표본에서는 일반 소거 목표0.6–1.0초를 충족하지만 전체 보드·장치 보장은 아닙니다.

## 원인부터 측정
`main.gd`에서 확정→낙하 시작(소거 연출), 낙하 시작→READY의 벽시계를 기록하고, `board_motion.gd`에서 지지 계산·공급 계산·충돌 계산 CPU 시간을 별도로 누적했습니다. 고정120Hz의 시뮬레이션 시간에는 공급 완료·전체 유입·마지막 안정 확인 시점도 기록했습니다. MovieWriter 없이 실제 렌더를 실행했으며, 동시 검사·내보내기·인코딩은 없었습니다.

측정 환경은 Godot4.6.3/Linux/Xorg/Mesa llvmpipe 소프트웨어 OpenGL입니다. 실제 오디오 장치가 없어 dummy driver를 사용합니다. 엔진 입력 자동화이며 실물 터치 지연 측정은 아닙니다.

CPU 시간은 낙하 벽시계 **안에 포함**되고 공급·이동·안정화는 동시에 일어나므로 이 행들을 더하면 안 됩니다. 공급 시점과 마지막 확인은 시뮬레이션 시간입니다. 전체 유입 이후 READY까지 첫 일반117ms, 긴 연쇄200ms이며 이 중 마지막58ms가 연속 저속 확인입니다. 나머지를 전부 불필요한 대기로 간주하지 않았습니다. 벽시계에서 계측 CPU를 뺀 값에는 렌더·스케줄링·프레임 대기가 섞여 있어 모두 CPU 지연이라고 단정하지 않습니다.

첫 일반2개의 전 상태에서는 낙하 벽시계2.14초 중 충돌 계산만1.91초였습니다. 공급 계산은1.4ms, 지지 계산46.6ms였습니다. 중력이나 안정 대기를 바꿀 이유보다 계산 접근 비용을 줄일 근거가 명확했습니다.

## 변경과 보존
1. 한 물리 스텝 중 앵커는 변하지 않으므로 두 고정체 쌍을 미리 제외하고 원래 i/j 순서의 후보를 한 번 만듭니다. 거리로 후보를 생략하지 않아 후속 보정으로 생긴 충돌도 놓치지 않습니다.
2. 반복 충돌 계산에서 Dictionary 속성을 계속 읽는 대신 `PackedVector2Array` 위치·속도와 형식 지정 반지름·가중치 배열을 사용합니다. 한 스텝 후 원래 패널 데이터에 반영합니다. 중간 계산을 읽는 다른 소비자는 없습니다.

후보 목록만 재사용한 첫 시도는 긴 연쇄6.10→4.99초였지만 첫 일반소거는2.34→2.71초로 악화했습니다. [실패/부분 개선 측정](../evidence/performance/pairs-only.json)을 보존했고 이를 최종 성과로 선택하지 않았습니다.

중력6000, 속도상한1100,120Hz, 최대128회 보정/0.04px 조기 종료, 위쪽 입구 선택, 접촉 판정, 감쇠, 공급 간격, READY 조건은 그대로입니다. READY는 이미 완전한 sleep과 분리되어 있습니다. 이번에는 완화하지 않았습니다. 겹치거나 떠 있는 패널을 고정해 시간을 줄이지 않았습니다.
