# 저장 실패 및 종료 안정화

2026-10-22. 기준 3397e37. 기존 후보를 보존한 후속 수정. [수정 전 설계](SAVE_RECOVERY_DESIGN.md).

## 수정한 사용자 동작

이전 구현은 파일 쓰기/완료 장벽 실패에도 dirty를 해제해, 이후 입력이 없으면 다시 저장하지 않았다. 실제 tmp 경로 장애로 6개 검사 중 4개 실패를 재현했다(`baseline-save.log`). 이제 실패한 요청과 마지막 완료 상태를 유지하며 최초 실패 뒤 1초/3초/7초 간격으로 세 번만 자동 재시도한다. 연타·프레임·새 행동은 실패 예산을 무한 초기화하지 않는다. 소진 뒤 안내를 눌러 명시적으로 다시 시도할 수 있다. 성공한 뒤에만 경고가 사라진다.

완료되지 않은 연쇄/낙하/반격이나 누른 채 입력은 저장하지 않는다. 재시도 중 애니메이션에서는 보관해 둔 마지막 완료 상태만 쓴다. 이때 저장 성공이 다음 행동의 dirty를 지우지 않도록 했다. 보상/구매를 재실행하지 않고 이미 확정된 거래 장부를 기록한다. 완료 기록은 일반 저장의 재시도 예산과 별도로 최초 시도한다.

정상 창 닫기는 마지막 완료 상태/완료 장벽을 한 번 더 확인한다. 쓰기가 실패하면 **저장 재시도 후 종료 / 저장 없이 종료**를 명시적으로 고른다. 영구 장애로 사용자를 무한 대기시키지 않는다. 완료 장벽이 실패한 뒤 새 탐험도 확인을 거쳐 이전 저장을 보관한다. 보관 실패는 현재 탐험을 초기화하지 않는다. 현재 파일의 read 오류를 손상으로 오인해 원본을 덮어쓰지 않는다.

## 보장하지 않는 것

파일시스템이 계속 쓰기를 거부하면 저장 성공을 보장할 수 없다. **저장 없이 종료, 강제 종료 또는 전원 차단 후에는 이전 체크포인트가 재개될 수 있다.** 최초 저장 자체가 실패했다면 재개할 저장이 없을 수 있다. 완료 기록도 쓰지 못했다면 이전 진행이 남는다. 전원 차단/fsync 내구성, 동시 여러 프로세스 저장, Windows 실기 실행, 클라우드 동기화는 보장하지 않는다. 자동 재시도는 창 종료 확인 화면에서는 멈추고 사용자의 선택을 기다린다.

## 오디오 진단과 범위

게임 코드를 전혀 사용하지 않는 AudioStreamPlayer 하나의 play/stop/free/quit로도 Godot 4.6.3 Dummy에서 WAV/PlaybackWAV 종료 경고를 재현했다(실시간 및 fixed-fps 모두). 기존 게임 오디오 노드는 이미 exit_tree에서 stop, stream=null, voices.clear를 수행한다. 12회 생성/정지/해제의 weakref를 관찰하면 마지막 재생 참조도 이후 해제된다. 즉 한 SceneTree 프레임은 비동기 오디오 정리 완료의 증거가 아니다. 관련 기존 보고: [Godot #76745](https://github.com/godotengine/godot/issues/76745), 2026-10-22 조회. 그 보고를 현재 버전의 수정 보증으로 사용하지 않았다.

테스트용 `audio_teardown.gd`는 실제 소리를 재생한 뒤 weakref가 없어질 때까지 CPU를 양보하며 최대1초만 관찰한다. 임의 고정 대기나 경고 억제로 통과시키지 않으며 제한 초과는 실패다. 프로세스 재개 검사 및 정상 실행 harness가 이를 사용한다. 실제 main scene play/reset/free 8회씩 fixed-fps/실시간 두 모드도 검사했다. **제품 오디오 파형·볼륨·재생 타이밍은 변경하지 않았다.** 즉시 종료 최소 재현의 엔진 경고가 제품 전체에서 해결됐다고 주장하지 않는다. 실물 오디오 출력도 미검증이다.

## 검증

격리된 /tmp 저장만 사용. 실제 open/rename 장애와 test-only read-only/부분 쓰기(용량 부족)/rename/read 오류 주입을 구분한다. 실제 디스크를 채우거나 권한·마운트를 바꾸지 않았다. 주입기는 실패한 tmp bytes를 실제로 만들며 current/backup 원본과 복구 상태를 검사한다.

결과 및 실행 명령은 `evidence/save-recovery/`에 보존한다. 추가 검사는 `tests/test_save_recovery.gd`, `tests/test_quit_failure.gd`, `tests/test_audio_teardown.gd`, 창 검사는 `quality_window_driver.py --lifecycle-ui --save-failure`로 재현한다. 최종 집계는 같은 디렉터리 `summary.json`을 참조한다. GitHub 하네스 CI와 이 환경의 Godot 실행 검증은 별개다.

초기 테스트 작성 시 SceneTree에서 Node 상수를 한정하지 않은 parse 오류, 정상 패배 실행에 잘못 지정한 정책 옵션, 원래 창 검사의 hit-controls 옵션 누락을 그대로 기록했다. 각 원인을 수정해 의도한 범위를 다시 실행했다. 초기 정상 'loss' 경로는 실제 승리였으므로 패배 근거로 사용하지 않는다.

### 최종 실행 결과

- 새 실패/복구62개, 기존 저장24개·컨트롤러30개, 기존 회귀52개 통과. 마지막 다중 포인터 재시도 경계2개는 실패를 먼저 확인한 뒤 수정했고 interaction/controller도 재검사했다.
- 기존 창90개×360×640/390×844/720×1080, short79개 통과. 기존 lifecycle29개를 유지한 실패/재시도/종료 확장42개×360×640/720×1080 통과. 작은 창에서 경고·종료 선택 화면을 직접 확인했다.
- 자식 프로세스87회, 전체 연속/단계별 재개 비교2회: 리오22소거·노아18소거 승리까지 해시 일치. 이87회 로그는 오디오 종료 경고0개. held/busy/attack 중단과 정상 새 시드·고정 시드도 포함.
- 저장을 켠 별도 정상 입력 플레이: 리오 승리19소거 HP30, 패배20소거 HP0, 둘 다 새 전투까지. 프로세스 비교와 정책/입력 경로가 달라 승리 행동수는 서로 다른 실행 결과다.
- 실제 일반 프로젝트 X11 입력에서 held 종료→재시작→이어하기→새 입력 통과. Dummy 오디오이며 장치 청취가 아니다. Pillow 사용 예정 중단 경고는 native runner 로그에 남아 있으며 게임 오류는 아니다.
- 실제 main scene sound/play/reset/free8회×실시간/fixed-fps 통과, 해당 로그 경고0개. 최소 즉시 종료 재현의 WAV/Playback 경고는 여전히 한계로 남긴다.
- 로컬 하네스 config 및 unittest5개 통과. 원래 실패 로그/잘못 지정했던 테스트 옵션의 실행도 증거에서 삭제하지 않았다.

검증은 gameplay/physics/art/PCM 변경 없이 저장과 종료 경계만 다룬다. Windows 후보는 별도로 내보내며 실제 Windows 실행 완료로 표현하지 않는다.
